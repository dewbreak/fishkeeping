# 有界视频取帧与低 token 证据

实施日期：2026-10-28。视频路径是本地解码与稀疏取帧，再由调用方显式发送多张图片给视觉模型；不是将视频 Base64 当文字，也不声称模型观看了全部视频。当前不解码音轨，不做语音转写、逐帧目标追踪或连续动作证明。GitHub 项目与真实媒体来源另见本轮调研和验收记录。

## 输入与计算上限

`VideoRequest` 接受 scope、视频 Base64、问题、`max_frames=6`、`strategy="adaptive"`、`max_chars=6000`，以及可选的 `start_seconds=0`、`end_seconds=null`。问题最多 1000 字符，输出帧预算 2–12，来源 JSON 预算 2000–10000 字符。

只接受 MP4-family（ISO BMFF `ftyp`）或 AVI 文件，最多 24 MiB、180 秒、6000 个解码帧、12M 单帧像素、8192 最长边。拒绝 URL、播放列表和无有效帧率/帧数元数据的输入。只靠容器声明不能证明内容可信；本机解码器仍需保持安全更新。

OpenCV 延迟导入，在独立 Python 子进程中运行，默认墙钟超时 45 秒（可配置 1–60 秒）。父进程不让阻塞的原生解码器驻留在 HTTP 线程；超时杀死子进程，释放临时文件。FFmpeg backend 显式使用 file 协议白名单并关闭外部 data reference。标准输出/错误不向客户端泄露，服务不启动额外远程程序。临时视频不进入记忆库或 Git；生产环境按自身安全策略配置临时目录。

单个 `VideoProcessor` 同时最多解码一条请求，繁忙时快速抛出 `VideoBusyError`，避免多个视频争抢内存/CPU。该限制是每个服务进程的限制，不是跨机器配额。子进程有时长、解码帧数、像素和结果文件预算，但没有宣称操作系统级硬内存隔离。

## 时间戳与残缺流

从第一帧开始按顺序解码；每帧读取 backend 的 `CAP_PROP_POS_MSEC`，要求严格递增且有限，不使用 `frame_index/fps` 伪造时间戳。来源同时保留实际帧索引、末个实际 PTS 和容器声明时长；后者只是元数据估计。异常时间戳被拒绝。

`capture.read()` 提前失败不能直接视为完整 EOF：声明帧数与实际解码数差异容忍 `max(2 帧, ceil(声明帧数 × 1%))`；声明时长与实际 PTS 跨度（加一个声明帧间隔）的差异容忍 `max(250ms, 2/fps)`。超过任一容差拒绝输出。此处为保守工程容差，允许轻微元数据误差，不保证识别被同步篡改元数据的损坏文件；不支持的 codec/容器可能被拒绝，调用方可显式转换素材后重试。

## 候选与帧选择

全片最多 90 个均匀时间探针，保留首尾实际解码帧。时间探针间距至少 0.1 秒；元数据声明较长时按声明时长调整间距。每张候选 JPEG 最长边不超过 1280，逐级调整至 960/640 和质量上限，以保证每张 ≤256 KiB、全部候选结果文件 ≤48 MiB。压缩是本地传输/内存预算，不等于视觉 tokens 按文件字节同比减少。

`uniform` 按候选序列均匀选择直到帧预算，作为固定基线。`adaptive` 保留窗口首尾，先分配部分时间覆盖锚点，再按相邻候选的 RGB 16×16 平均绝对差、相对已选帧的新颖度与时间间隔填充预算。阈值是固定工程启发式，不按答案或真实测试标签调参；问题正文不会影响选帧。

近重复只用于节省额外帧，首尾仍保留；同一画面在不同时间重复出现可以保留相同图片哈希。因此 A→B→A 不会被全局哈希去重错误变成 A→B。`frame_index`、帧 ID 和时间戳唯一递增，图片 SHA256 可以重复。原始视频 SHA256 与每张最终 JPEG SHA256 分别记录。

`observed_transitions` 是候选之间超过固定颜色变化阈值的计数，不是真实剪辑点或真实事件数量。`represented_transitions` 只计选中的对应候选；帧预算遗漏这些变化或最大选帧时间间隔超过 10 秒时，`requires_review=true`。快速动作、短暂物体、细字幕与探针间的变化仍可能漏掉，即使这个标记为 false 也不保证问题答案可见。

## 显式分析时间窗

调用方可根据用户问题指定 `start_seconds/end_seconds`，不由评测金标准或模型答案反推窗口。仍完整执行有界解码，但只在窗口内的候选中选帧；窗口必须落在实际解码时间轴内且包含至少两个候选，否则拒绝。帧保留原视频 PTS，不重置为 0。

证据分别给出全片 `duration_seconds/decoded_frames/candidate_count`，与窗口 `analysis_start_seconds/analysis_end_seconds/window_candidate_count`。变化计数、重复计数和 `max_gap_seconds` 基于窗口，最大间隙包含窗口边缘到首末选中帧的空档。非完整窗口始终写明“只代表该窗口”；降低整段上传范围不能被宣传成仍完整理解了全片。

## 来源和集成

`VideoProcessor.analyze(VideoRequest)` 返回 `VideoEvidence.selected_frames`，每帧包括 ID、帧索引、PTS、SHA256、JPEG Base64、尺寸和选择原因。`packed` 不含像素 Base64，而是视频身份、方法/版本、参数、时间覆盖、遗漏风险及每帧来源，适合可靠事件的 tool 消息。字符预算不足返回错误，要求降低帧数，不截掉部分来源冒充完整证据。

API/SDK、可靠视频事件与 DeepSeek 适配器由服务层组合；本模块零模型 API 调用、零自动付费回退。无论图像、字幕还是 OCR，都只是参考证据，不获得系统指令权限。视频、候选图片和临时文件不写入用户记忆库。

## 验证范围

`tests/test_video.py` 的 fake decoder/capture 在不安装 OpenCV 的普通 CI 运行，覆盖 2–12 帧预算、静态重复、A→B→A、可变帧间隔、时间窗与边缘间隙、超范围、无效 PTS/metadata、短暂 EOF、子进程超时清理、并发拒绝及来源字符上限。

本机还实际生成 60 帧 / 10fps 的合成 AVI，经 OpenCV 5.0.0 的 FFmpeg 子进程顺序解码得到末个 PTS=5.9 秒；自适应选出 5 帧，2.0 秒与 4.0 秒的颜色变化都保留。它只验证本机 codec/子进程/时序链路，不是复杂真实视频准确率；真实视频的固定标签、采样遗漏和模型 usage 由主验收单独报告。
